# Intake channel is an enum; origin is a postal code

Customers outside a Store's city send their Items in by shipping company (JNE, J&T, SiCepat) instead of carrying them to a counter, and the operator wants two things: to tell those Orders apart, and to record **where the Items came from** so the shop can see which places generate demand it does not yet serve at a counter. Midway through the design the same question was asked of Courier pickups — record the customer's postal code there too. We decided to add an **`orders.intake_channel` enum** (`walk_in` / `courier` / `shipped`) and a single nullable **`orders.origin_postal_code`** FK into a new `postal_codes` reference table, and deliberately **not** to model the return leg, not to ask walk-ins where they came from, and not to store a city.

This **amends [ADR-0010](0010-courier-role-login-only-excluded-by-allowlist.md)**, whose central decision was that `orders.collected_by` alone marks how an Order arrived ("there is no separate `is_delivery` boolean — the courier reference **is** the marker"). That held while there were two ways in. It does not survive a third.

## Considered options

- **`intake_channel` enum + `origin_postal_code` (chosen).** One column says how the Items arrived; a separate, optional column says where from. The two facts are independent, so they get independent columns.
- **A non-null origin city marks the Order as shipped-in.** The first choice in this design, and correct while a location existed on shipped-in Orders only — it followed ADR-0010's own discipline of letting a reference double as the marker, and a FK cannot be a typo the way ADR-0010's rejected free-text courier name could. Killed by the Courier postal code: once two of three channels carry a location, a location can no longer say which channel. It also silently filed an unreadable shipping label as a walk-in.
- **`is_shipped_in` boolean alongside `collected_by`.** Rejected — two columns encoding three states, with `is_shipped_in = true` *and* a Courier set as a nonsense combination needing its own CHECK. The enum encodes the same three states in one column that cannot express a fourth.
- **A city FK instead of a postal code.** Rejected, even though "which city do we open in" is literally the question. A postal code resolves to a kota/kabupaten (99.3% of the time) and a provinsi (always), so the city ranking is a JOIN away and the sub-city detail that actually picks a shoplot rides along in the same row. Five digits are also faster to enter on a tablet than a typeahead over 514 city names.
- **Postal code with a city column as fallback.** Rejected — captures a few more Orders whose shipping label shows a city and no kode pos, at the price of two nullable location columns, a rule that they must agree, and a `coalesce` in every query forever.
- **Free-text city.** Rejected for the reason ADR-0010 rejected a free-text courier name: group-by is the entire purpose here, and `Bandung` / `bandung` / `BDG` / `Kota Bandung` do not group.
- **Ask walk-ins for their location too.** Rejected for v1 — it is one more field on the busiest flow, most likely to sit empty, so the walk-in numbers would be a biased sample rather than a count. Courier postal codes already cover the metro area walk-ins are drawn from.
- **Model the return leg** (return shipping fee, airway bill, what pickup means with no customer present). Rejected — see Consequences. Same scoping call ADR-0010 made for the courier return leg.

## Decisions

- **`orders.intake_channel` is `intakeChannelEnum('walk_in','courier','shipped')`, `NOT NULL DEFAULT 'walk_in'`.** Existing rows backfill from `collected_by`: null → `walk_in`, non-null → `courier`. No existing Order is `shipped`.
- **`collected_by` keeps its meaning but loses its job as the marker.** A Courier is still who fetched the Items; the channel column is now what says an Order was fetched at all. Enforced: `(intake_channel = 'courier') = (collected_by IS NOT NULL)`.
- **`orders.origin_postal_code` is a nullable FK → `postal_codes.code`.** Where the Items came from, independent of how they got here. A `walk_in` Order must leave it null — the customer is standing at the counter, so there is nothing to record.
- **Both invariants are DB CHECK constraints**, not service-layer asserts. The channel axis is the kind of thing a future import script gets wrong quietly.
- **`postal_codes` is reference data keyed by the 5-digit `code`**, carrying `city` (the kota/kabupaten), `province`, and `districts`. **`districts` is a display-and-search string, never a grouping key** — measured against the source data, 609 of 9,999 codes (6.1%) cover more than one kecamatan, so kecamatan is simply not a function of a postal code and a single-kecamatan column would be a lie. It earns its place anyway: a cashier typing "Depok" gets ~30 codes that are otherwise indistinguishable. **No `kelurahan` column** — one code covers many. **No `is_active` column either**: the Activation rules in `CONTEXT.md` govern catalog rows someone drafts and then puts on sale. A kode pos is neither drafted nor sellable. Do not "fix" this into consistency with Service and Product.
- **The location is optional on every channel that may carry one.** A blank means the shop does not know, which is a truthful answer and a better one than a cashier guessing a plausible code to clear a required field. The cashier creating the Order is never at the pickup address (ADR-0010: Items must be physically present at create), so the code arrives second-hand from the customer or the courier, and most people do not know their own kode pos.
- **Because the location is optional, the reports panel prints a coverage figure** — "origin known on 62% of courier Orders" — beside the ranking. Without it, a column quietly rotting to all-blank looks exactly like a ranking with few entries.
- **The picker searches both ways**: type `16424` and get Cimanggis, Depok; type `cimanggis` and get 16424. Recording a postal code the customer cannot recite is otherwise not possible.
- **Set at create, editable on the order detail by anyone who may take an Order** — admin, cashier and worker, since [ADR-0004](0004-role-capabilities-v1.md)'s 2026-09-05 amendment opened the POS to workers. It reuses `assertCanCreateOrder`, deliberately: whoever can record how an Order arrived can also correct it. (ADR-0010 said "cashier + admin" for `collected_by`; that wording predates the amendment and was never true afterwards.) A wrong origin is a corrupt research record, so correction is a first-class path rather than a create-only field.
- **Overseas parcels are `shipped` with a null origin.** There is no "Other" row in `postal_codes` and no free-text fallback — the table holds Indonesian codes only, so nothing can pollute the ranking. A parcel from Singapore is still honestly counted as shipped-in; it simply contributes to no city. Staff note the country in `orders.notes`.
- **A shipped-in Order's Drop-off photo is the sealed parcel with the shipping label visible, shot before opening.** The glossary defines that photo as proof of a handover "across the counter", and there is no counter here. The parcel shot is better evidence than the contents — it proves what arrived, from whom, and by which company — and it is the same document the postal code is read off.
- **A shipped-in Order books to whichever Store opened the parcel.** Store attribution is unchanged.

## Consequences

- **The return leg is out of scope and stays manual.** Shipping the finished Items back — the return fee, the airway bill, and what pickup means when no customer appears at the counter to speak the pickup code — is handled by staff outside the system, like the goodwill voucher and the 30-day collection limit already are. Recorded here so it is not re-litigated as an oversight. Three specific things would have to be answered first: a shipping fee fits neither an OrderProduct (it would decrement stock) nor a Service (it would land in a Category and distort revenue-by-Category); the pickup code becomes theatre when the cashier both holds and enters it; and the blocking Pickup photo becomes a shot of the outbound parcel, which is fine but needs saying.
- **The ranking cannot see walk-ins**, who are the overwhelming majority of Orders. Read the panel as "where is there demand we do not already capture at a counter", never as "where our customers live". A Kemang regular who drives in from Depok every month contributes nothing to it.
- **Kota and Kabupaten of the same name are separate rows** — `KOTA BANDUNG` and `KAB. BANDUNG` are different markets, which is a real improvement over asking a cashier to choose between two near-identical names. **The city is not perfectly derivable, though:** 69 of 9,999 codes (0.7%) straddle two regencies, and not all of them are remote — `15157` spans `KAB. TANGERANG` and `KOTA TANGERANG`, inside the BSD store's own market. Each such code is assigned to whichever regency holds most of its villages, so 69 rows carry a known, documented approximation; the error is only ever between two adjacent regencies in the same province. Province, by contrast, is 100% derivable — no code crosses one. Metro-level sums remain the number to trust when siting a store.
- **`postal_codes` ships through the migration ledger, not a seed script.** The 9,999 rows are a data migration (`20260911165309_postal_codes_reference_data`), so every environment gets them exactly once by running `migrate`, with nothing to remember. The first cut made it a separate idempotent seed script; that was wrong, because it behaves like a migration — run once per database, never again — while sitting outside the ledger, and the failure mode is silent: migrate production, forget the seed, and the picker returns an empty list with no error anywhere. The `ON CONFLICT (code) DO NOTHING` clause survives from that version and is worth keeping, since it lets the same file be replayed against a database that already has the rows. **Provenance:** generated from `kode-wilayah-id` v1.2.0 (MIT, BPS + Kemendagri codes, updated 2026-05) by a checked-in generator script that now prints SQL. The package is **not** a dependency — going to the registry on demand would make a migration depend on something that can be unpublished. Refreshing after a BPS boundary change means a new custom migration, which is the correct way to change production data anyway.
- **The new reports panel must not inherit the range-panel Revenue bug.** `CONTEXT.md` flags that the seven range panels sum pre-discount line values under a Revenue label, which is Gross sales. A panel that ranks cities by money must either label its figure Gross sales or compute Revenue correctly; it must not copy a neighbouring panel's query.
- **The enum and the CHECKs ship through the migration ledger**: `bun run generate`, hand-edit the generated SQL to insert the backfill, `migrate:dev`, `drift:dev`, then `drift:prod` → `migrate:prod` before the next deploy. There is no `push:prod`, and `push:dev` is throwaway local prototyping only — see `packages/server/AGENTS.md`. Adding a CHECK to a populated `orders` table requires the backfill to land first **in the same migration**: the column default writes `walk_in` into every existing row, which is wrong for the `collected_by IS NOT NULL` ones and would fail the CHECK. `drift` does not diff CHECK constraints, so verify both against `pg_constraint` after `migrate:prod` — an empty drift is not proof.
- **ADR-0010's "the courier reference is the marker" sentence is now historical.** Code reading `collected_by IS NOT NULL` to mean "delivered" still gets the right answer, because the CHECK keeps the two in lockstep — but new code should read `intake_channel`.
