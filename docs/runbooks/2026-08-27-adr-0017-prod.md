# Prod deploy: ADR-0017 Item

One deploy window, four steps, in order. The code is already merged ahead of the
schema, so **every order read 500s between the code going live and step 2
finishing**. Deploy the container after step 4, not before.

Prod differs from dev by exactly this change and nothing else — verified
2026-08-27 by diffing `information_schema` on both (27 vs 26 tables, 231 vs 228
columns, every difference an ADR-0017 move).

## Why this one is by hand

`push` would add the NOT NULL `item_id` against populated rows and drop
`brand`/`color`/`model`/`size`/`item_code` before anything had copied them,
losing every tag code in the shop — and no generator writes the `INSERT..SELECT`
that has to run between the two halves. So the file is applied directly.

It is intended to be the last schema change this repo applies by hand.

## 1. Confirm prod is where you think it is

```bash
cd packages/server
bun run explain:prod
```

Read-only. Expect a plan that is exactly the ADR-0017 delta — `items` created,
`item_id` added, the five columns dropped. **Anything else is unrelated drift:
stop and deal with it as its own change.** If the plan is empty, the migration
has already run; skip to step 3.

## 2. Apply the migration

```bash
cd packages/server
bun -e 'import{Pool}from"@neondatabase/serverless";
const p=new Pool({connectionString:process.env.DATABASE_URL_PROD});
const c=await p.connect();
try{ await c.query(await Bun.file(
  "migrations/0001-adr-0017-item-groups-order-services.sql").text());
  console.log("committed"); } finally { c.release(); await p.end(); }'
```

One transaction. The file asserts before it destroys — it refuses if any
treatment row has a NULL `item_code` or `order_id`, and refuses again after the
backfill if any row still has no `item_id`. A failure at any statement leaves
prod exactly as it was.

Verify:

```sql
SELECT (SELECT count(*) FROM items)                              AS items,
       (SELECT count(*) FROM orders_services)                    AS lines,
       (SELECT count(*) FROM orders_services WHERE item_id IS NULL) AS unlinked;
```

`items` must equal `lines`, and `unlinked` must be 0. The backfill is one Item
per existing treatment — lossless, and it groups nothing retroactively.

## 3. Backfill `orders.status`

The cancelled-sibling fix in `deriveOrderStatus` changed what the rollup returns
for an order whose live lines are all queued but which carries a cancelled line:
`processing` → `created`. The fix only corrects rows something later touches, so
stored rows stay stale until this runs. Must come after step 2 — it reads
`orders_services`.

```bash
cd packages/server
bun -e 'import{db}from"@/db";
import{recomputeOrderRollup}from"@/modules/orders/order-status-machine";
const stale=await db.$client.query(`
  select o.id, o.code, o.status from orders o
  where exists (select 1 from orders_services x where x.order_id=o.id and x.status=$$cancelled$$)
    and not exists (select 1 from orders_services x where x.order_id=o.id
                    and x.status not in ($$cancelled$$,$$queued$$))
    and exists (select 1 from orders_services x where x.order_id=o.id and x.status=$$queued$$)`);
console.log(`${stale.rows.length} order(s) to recompute`);
for (const r of stale.rows) {
  await db.transaction(async (tx)=>{ await recomputeOrderRollup(tx, r.id, 1); });
  const a=await db.$client.query("select status from orders where id=$1",[r.id]);
  console.log(`  ${r.code}: ${r.status} -> ${a.rows[0].status}`);
}
process.exit(0);'
```

Set `NODE_ENV` so `src/db/index.ts` picks prod. Dev had exactly 1 such order;
prod's count is unknown until you run it. Zero is a valid answer.

## 4. Deploy the container

Only now. The code has been ahead of the schema since the ADR-0017 merge, so
until step 2 landed there was nothing to deploy into.

Smoke test, as `admin`:

- an order detail page renders its Items with tags and descriptors
- `/queue?storeId=<id>` shows one card per object
- a paid, fully-ready order offers `Pick up · N`
- `/track?code=…&phone=…` groups by object

## Rollback

Steps 1, 3 and 4 are safe to retry. Step 2 is the only irreversible one: it
drops five columns after copying them into `items`. There is no down migration —
recovering the old shape means restoring from a Neon branch or PITR taken before
the window. **Take that branch before step 2.**
