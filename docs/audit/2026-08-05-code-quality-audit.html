00Verdict

The blunt version, before the itemised list.

This is not ugly code. It is well-organised, consistently formatted, genuinely tested in the places that matter most, and the comments — where they exist — explain why rather than restating the line below them. Most codebases this size are worse. Someone has been paying attention.

The problem is narrower and more interesting than ugliness: several important invariants are true by convention rather than by construction. The code is correct today because three or four unrelated mechanisms happen to agree, not because anything states the rule or would fail loudly if it broke. That is the category of defect that survives code review — every individual line looks fine — and then costs a weekend a year later.

Section 01 is the clearest example and the reason this report was re-cut. The money path is correct, and it is correct by accident in three places at once. No rule set flags any of it.

Beyond that, the ugliness that does exist is concentrated, not diffuse. Four files carry most of it — financial-panel.tsx, lib/api.ts, report-range.repository.ts, worker.index.tsx. Roughly 5,000 of 52,000 lines. The other 90% of the codebase is fine and should be left alone.

What I would not spend time on. Of the 39 findings here, about a dozen are observations rather than problems — S13, W12, W15, W16, W17 and most of the Low band. They are recorded for completeness. A long audit invites the mistake of treating length as a work queue; it is not one. If you fix only M1, M2, S1, S2 and C1, you will have captured most of the real value in this document.

01Money & data integrity

This section exists because I stopped consulting rule sets and started asking what I would ask in review: where does the money live, what guarantees its shape, and what happens the day that guarantee is wrong? No linter, and neither Vercel rule set, has an opinion about any of the five findings below. All five were verified against the live dev database, not just read off the schema file.

Read this first. Nothing here is currently producing wrong numbers. Every claim below was checked, and the money is right today. The finding is why it is right: three unrelated mechanisms independently coerce money into whole rupiah, none of them says so, and the database is configured to round silently instead of complaining. That is a correctness result that no one owns.

M1HighShipped #78

orders.total is the only nullable money column, and three CHECK constraints depend on it

data-integritymoneyone-line-fix

Evidence

Four money columns on orders. Three are .notNull(). One is not: 

discount:        decimal("discount",        { precision: 12 }).default("0").notNull(),  // :449
paid_amount:     decimal("paid_amount",     { precision: 12 }).default("0").notNull(),  // :460
refunded_amount: decimal("refunded_amount", { precision: 12 }).default("0").notNull(),  // :471

// snapshot
total:           decimal("total",           { precision: 12 }).default("0"),            // :481  ← no .notNull()

Confirmed against the live dev database — this is the real column state, not just the source: 

column_name      | numeric_precision | numeric_scale | is_nullable
-----------------+-------------------+---------------+------------
discount         |        12         |       0       |     NO
paid_amount      |        12         |       0       |     NO
refunded_amount  |        12         |       0       |     NO
total            |        12         |       0       |     YES     ←

Now look at which constraints reference it:

check("total_non_negative_check",  sql`${table.total} >= 0`),                  // :498
check("discount_valid_check",      sql`(${table.total}) >= ${table.discount}`), // :505
check("paid_amount_valid_check",   sql`${table.paid_amount} <= ${table.total}`) // :507

Why it matters

A Postgres CHECK fails only on FALSE. NULL makes it UNKNOWN, which passes. So a single NULL in total silently disarms three of the five money guards on the orders table at once — an order could then carry a discount larger than its total, or record more money collected than was ever owed, and every constraint would still be satisfied.

These three checks are the most valuable lines in the schema. They are the reason a pricing bug becomes a failed insert instead of a wrong invoice. Right now their protection is conditional on a column that is allowed to be absent.

It also leaks outward. total types as string | null, so every consumer has to defend against a null that the business model does not actually permit — 17 occurrences of total ?? 0 across the web app, each one a small lie about the domain (an order with no total is not an order worth zero rupiah; it is a bug).

What to do

Add .notNull() and push. Zero rows violate it today — I counted: 

SELECT count(*) FROM orders WHERE total IS NULL;  →  0

No backfill, no migration risk, no data cleanup. It is a one-word change that re-arms three constraints and deletes 17 defensive coalesces downstream. This is the highest value-per-character fix in the entire report.

M2HighShipped #78

"Money is whole rupiah" is a real invariant that nothing in the codebase states — and the database enforces it by silently rounding

moneyimplicit-invariantsilent-failure

Evidence

Twenty-two money columns are declared with a precision and no scale: 

decimal("price",       { precision: 12 })   // ×22 across products, services, campaigns,
decimal("total",       { precision: 12 })   //     orders, order_services, order_products,
decimal("applied_amount", { precision: 12 })//     order_refunds, order_refund_items …

In Postgres, numeric(12) means numeric(12, 0) — precision twelve, scale zero. Whole numbers only. The live database confirms numeric_scale = 0 on every one of them.

That this is implicit rather than intended is visible two lines away in the same file, where the only columns that do declare a scale are the ones where somebody thought about it: 

latitude:  decimal("latitude",  { precision: 11, scale: 8 }).notNull(),  // :58
longitude: decimal("longitude", { precision: 11, scale: 8 }).notNull(),  // :59

The invariant holds today because three unrelated pieces of code each independently force integers, none of them aware of the others:

  • getNumericValue strips every non-digit from money input at the HTTP boundary — common.ts:7
  • Math.round(contribution) at the end of every campaign discount calculation — schema/discount.ts:91
  • every price read back out of the database is already integral, so arithmetic over prices stays integral

Why it matters

The failure mode is the bad one. numeric(12,0) does not reject 1500.75 — it stores 1501. No error, no warning, no log line. If any one of those three mechanisms is removed or bypassed by a future contributor, money quietly becomes wrong by up to half a rupiah per operation and nothing anywhere fails.

For IDR the rule is almost certainly correct — Indonesian retail does not transact in sen. That is exactly why it deserves to be written down: it is a business decision about currency granularity that currently exists only as an emergent property of a regex, a Math.round, and a default nobody chose.

A new contributor reading decimal("price", { precision: 12 }) has no way to know cents are impossible. The word "decimal" actively suggests the opposite.

What to do

Two changes, neither of which alters a single byte of stored data:

  1. Write scale: 0 explicitly on all 22 columns. The emitted DDL is identical, so push:dev is a no-op — but the schema now says what it means, and a reviewer who tries to add a cents-bearing column has to consciously break the pattern.
  2. Add one test asserting the boundary: feed "1500.75" through currencySchema and assert the result. Whatever the answer should be, pin it — right now the behaviour is defined by a regex written for a different reason (see M4).

Optionally, name the rule once in schema.ts: all monetary columns are whole IDR; there is no sub-unit. One comment retires the whole class of question.

How it shipped. Twenty-four columns, not twenty-two — the count here was low. Verified against both live databases rather than the schema file.

M3MediumShipped #78

.toFixed(2) writes cents into a column that cannot hold them

moneycode-that-lies

Evidence

packages/server/src/modules/orders/order.service.ts:254: 

cogs_snapshot: (Number(product.cogs) * item.qty).toFixed(2),

cogs_snapshot is decimal("cogs_snapshot", { precision: 12 }) — scale 0. The two decimal places are produced, sent to Postgres, and discarded on arrival.

Why it matters

No data is lost, because product.cogs is itself scale-0 and item.qty is an integer, so the product is always integral and .toFixed(2) only ever appends .00. Nothing is broken.

The problem is that the line asserts a precision the schema forbids. Someone wrote it believing cents existed here. The next person to read it will believe the same thing, and may reasonably conclude that fractional COGS is supported — it is right there in the code. This is how an implicit invariant (M2) gets broken: not by someone ignoring the rule, but by someone reading code that contradicts it.

For contrast, the two other .toFixed() calls on the server are correct and should stay — report-range.repository.ts:977 and :979 round rework_rate and items_per_hour, which are genuine ratios in a JSON response, not money bound for a column.

What to do

Drop the .toFixed(2); use String(Number(product.cogs) * item.qty). If the intent was defensive rounding, Math.round states that intent honestly and matches what the column will do anyway.

How it shipped. Kept Math.round rather than dropping the rounding, so the line says what the column will do. The test that fed it fractional COGS had been quietly changed to whole rupiah, which removed the only case exercising this line; the fraction is back and the assertion now pins the rounded result.

M4MediumShipped #78

currencySchema is a five-stage round-trip whose validation cannot fail

validationdead-codenaming

Evidence

packages/server/src/schema/common.ts:7 and :44 — the only guard on every money field that enters the API: 

const getNumericValue = (formattedValue: string): string =>
  formattedValue.replaceAll(/[^\d]/g, "");

export const currencySchema = (field: string) =>
  z
    .string(`${field} is required!`)
    .min(1, `${field} is required!`)
    .transform(getNumericValue)                                  // string → string
    .transform(Number)                                           // string → number
    .pipe(z.number().nonnegative(`${field} cannot be negative`))  // ← unreachable
    .pipe(z.coerce.string());                                    // number → string

Why it matters

Three separate problems, all in nine lines.

The negative check can never fire. getNumericValue has already deleted the minus sign by the time .nonnegative() runs. Input "-500" becomes "500" and validates as a perfectly good positive discount. The message "Discount cannot be negative" is unreachable code that reads like a live guarantee — worse than no check at all, because a reviewer sees it and stops worrying.

The function is named like an accessor and behaves like a lossy parser. getNumericValue("12.50") returns "1250". That is correct and deliberate for Indonesian formatting, where . is the thousands separator and "1.500" means fifteen hundred — but nothing in the name, the signature, or a comment says so. The parameter is called formattedValue, which is the only hint, and it does not survive to the call site. A contributor who assumes it parses decimals will introduce a 100× error and see no test fail.

The type round-trips for no one. String in, string out — and the very first thing the service does is convert it back: Number(orderPayload.discount) at order.service.ts:275. The schema's output type is fighting every consumer it has.

What to do

  • Rename to parseIndonesianCurrency (or similar) and give it the one-line comment that explains the separator convention. The name is the documentation here.
  • Either validate before sanitising — so "-500" is actually rejected — or delete the .nonnegative() and stop implying a check that does not exist. Rejecting is better: a cashier typing a negative discount has made a mistake worth surfacing.
  • Land on number as the output type and let the repository layer stringify at the Drizzle boundary, where it belongs.
M5MediumShipped #78

Money has two TypeScript types depending on which endpoint you called

api-contractroot-cause

Evidence

Inside a single function, order.service.ts writes a string and returns a number: 

await tx.update(ordersTable).set({
  total: grossTotal.toString(),        // :292 — string into the column
  discount: discountAmount.toString(),
})…

return {
  code, id: orderId,
  total: grossTotal,                   // :305 — number out to the caller
  total_after_discount: netTotal,
};

Every read path returns the Postgres numeric as a string, so POST /orders answers with total: 45000 while GET /orders/:id answers with total: "45000".

Why it matters

This is the root cause of a pattern that shows up roughly forty times in the web app and reads like noise until you know why it is there: 

const discount = Number(detail.discount ?? 0);      // order-money-summary.tsx:11
const net      = Number(detail.total ?? 0) - discount;
const grossTotal   = Number(detail.total ?? 0);     // refund-preview.ts:9
Number(line.product.price) * line.qty               // checkout-items-step.tsx:119

Every component that touches money re-coerces it, because money has no single type to rely on. Each Number() is individually harmless and collectively means the frontend has no money type at all — just strings that everyone agrees to convert, in forty places, correctly so far.

It compounds with M1: because total is also nullable, the idiom is not Number(x) but Number(x ?? 0), which converts a missing value into a valid-looking zero. A genuinely absent total renders as Rp 0 rather than failing visibly.

This is the same shape as C2: a small inconsistency at the server boundary paid for many times over in client-side ceremony.

What to do

Pick one representation and hold it at the boundary. Given the values are whole rupiah under 253 (M2), number is safe and is what every consumer wants — serialise money as a number in every response, including the reads. Then the ~40 Number() calls delete themselves, and with M1 fixed the ?? 0 goes too.

If you would rather keep strings on the wire, that is defensible — but then make createOrder return a string like everything else, and give the web a single toRupiah(value: string): number so the coercion lives in one place instead of forty.

How it shipped. Took the second option, not the preferred one. Serialising money as a number everywhere means rewriting every read path including the reports module, which is being overhauled separately — so createOrder now returns strings like every other endpoint, and one parseMoney/formatMoney pair holds the coercion. That pair also fixed a latent bug this finding did not reach: formatting "45000.00" by stripping non-digits prints Rp 4.500.000, a hundred times the price.

02Cross-cutting

Three findings that are neither a web problem nor a server problem — they are seams between the two, and each is the root cause of noise elsewhere in this report.

C1High

Store scoping is enforced in three layers, four different ways

multi-tenancyone-rule-one-place

Evidence

Enforced in routes:

  • packages/server/src/routes/admin/orders.ts — assertOrderAccess written out 15 times, once per /:id/* handler (lines 166, 180, 199, 223, 247, 269, 290, 310, 331, 353, 373, 394, 414, 433, 454, 477)
  • packages/server/src/routes/admin/reports.ts — assertStoreAccess written out 10 times (lines 41, 56, 70, 83, 96, 109, 122, 135, 148, 161)

And in services, with different semantics each time:

  • modules/orders/order.service.ts:111-117 — non-admin without store_id → collect ids into scopedStoreIds
  • modules/orders/order-queue.service.ts:102-116 — same case → return [] when the user has no stores
  • modules/orders/order-queue.service.ts:160-179 — same case → empty page; and admin without store_id throws BadRequestException
  • modules/complaints/complaint.service.ts:183-188 — a fourth copy
  • modules/shifts/shift.service.ts:22 — a bare assertStoreAccess

Why it matters

There is no single place that answers "is this endpoint store-scoped?" — you have to read every handler and every service to find out. The logic itself is correct everywhere I checked; the repetition is the defect. Add a sixteenth /orders/:id/… route and forget line one, and it silently serves another branch's order. Nothing fails, no test catches it, and the reviewer has fifteen correct examples above it to skim past.

The admin check in routes/admin/reports.ts:29-32 proves the team already knows the middleware shape — it just wasn't applied to the store check sitting three lines below it.

What to do

  1. One resolveStoreScope(user, requestedStoreId) in utils/authorization.ts returning a discriminated result (all / one / some / none), so the four divergent behaviours become four declared cases instead of four transcriptions.
  2. A .use("/:id/*") on the orders sub-app that runs assertOrderAccess once and stashes the order on the context. Fifteen call sites become zero.
  3. The same for routes/admin/reports.ts — see S4.
C2HighShipped #81

Two error styles on the server produce 25 Extract<…, { success: true}> in the web client

rpcconsistency

Evidence

  • packages/server/src/errors.ts — five HTTPException subclasses, and index.ts:23-26 renders them
  • Yet route files contain 35 return c.json(failure(…), status) and exactly 1 throw (routes/admin/orders.ts:155)
  • routes/admin/orders.ts uses both: throw new NotFoundException("Store not found") at 155, then return c.json(failure("Order not found"), 404) at 171 — two lines apart in spirit, same outcome on the wire
  • apps/web/src/lib/api.ts — 25 occurrences of Extract<InferResponseType<…>, { success: true }> (lines 84-241 and beyond)

Why it matters

A return c.json(failure(...)) is part of the handler's return type. A throw is not. So every endpoint that returns a failure inline makes InferResponseType a union, and the web app has to peel the success arm off by hand — 25 times, in the one file that is supposed to make the RPC boundary feel typed. Half the types in api.ts are plain (Customer, Store, Service) and half are wrapped, and the difference tells you nothing about the domain — only which error style that route happened to pick.

What to do

Standardise on throw new NotFoundException(...). The global onError already renders it to the identical body and status, so this is a mechanical edit with no behaviour change — and it deletes all 25 Extract<> wrappers on the other side of the boundary.

How it shipped. Thirty-five conversions across twelve files, not thirty-three across eleven — routes/public/orders.ts was missing from the evidence. And twelve of the twenty-five wrappers were already dead before the change: the nine reports routes, two shifts routes and the complaints list never returned inline failures. So the real footprint was thirteen wrappers. Login needed one extra step — it was the only route on raw zValidator, which kept its 400 body in the response type; it now uses the same wrapper as everything else.

C3MediumShipped #81

Three mechanisms for one timezone

dates

Evidence

  • packages/server/src/utils/date.ts:10-20 — dayjs .tz("Asia/Jakarta")
  • modules/reports/report-range.util.ts:4 — hand-rolled JAKARTA_OFFSET_MINUTES = 7 * 60 arithmetic
  • modules/reports/report-range.util.ts:7 — AT TIME ZONE 'Asia/Jakarta' pushed into SQL

Why it matters

All three agree today, and they will keep agreeing: WIB is a fixed UTC+7 with no DST. So this is not a bug. It is that packages/server/AGENTS.md explicitly mandates the dayjs helpers and says "do not inline dayjs().startOf('day')" — and the reports module quietly runs a third scheme that the standard doesn't mention. Leave the code alone — it's tested and correct. Add the exception to packages/server/AGENTS.md: reports compute buckets with fixed-offset arithmetic and AT TIME ZONE in SQL, deliberately, because they must match Postgres' bucketing exactly. One sentence closes the gap.

03Server — packages/server

The module pattern (route → service → repository) is followed consistently and the domain logic around money and order status is the strongest code in the repo. The problems are concentrated in two places: what happens when something goes wrong, and the reports module.

S1HighShipped #79

Unhandled 500s are silent — the error log is commented out

operabilityproduction

Evidence

packages/server/src/index.ts:53-54

  // console.error(err);
  return c.json(failure(err.message), StatusCodes.INTERNAL_SERVER_ERROR);

Why it matters

Any error that is neither an HTTPException nor a Postgres error carrying .detail falls through to this branch. The client gets a message; the server writes nothing. There is no stack, no route, no user id. The API deploys as a container (Dockerfile.vercel), so the only diagnostic surface is stdout — and this line is what would have written to it.

This is the cheapest fix in the report and the one most likely to matter at 9am on a Monday when a till stops taking orders.

What to do

Uncomment it, and log the request context alongside — method, path, and c.get("jwtPayload")?.id. Do not log the body.

S2HighShipped #79

Raw Postgres detail is returned to the client — and it contains customer PII

privacyerror-handling

Evidence

packages/server/src/index.ts:28-50

if (typeof err.cause === "object" && err.cause && "detail" in err.cause) {
  // ... map SQLSTATE to status ...
  return c.json(failure(err.cause.detail as string), statusCode);
}

The unique constraints this can fire on:

  • db/schema.ts:81 — customers.phone_number … .unique()
  • db/schema.ts:75 — customers.email … .unique()
  • db/schema.ts:42 — users.username … .unique()

Postgres' detail for SQLSTATE 23505 is literally Key (phone_number)=(+62812…) already exists. — the offending value, verbatim, in the HTTP error body. On the web side that string lands in toast.error(details?.data?.message) (apps/web/src/main.tsx:40), so a customer's phone number or email can be rendered on screen as an error message.

Scope — being accurate about this

Every route that can hit this sits behind adminMiddleware, so the audience is authenticated staff, not the public. This is not a data breach. It is customer PII leaving the database layer through an unintended channel, into a surface (toast text, and any future client-side error reporting) that was never designed to hold it.

What to do

Map the SQLSTATE to a message you own — "A customer with that phone number already exists" — and keep detail on the server, in the log from S1. There is already an isUniqueViolation() helper in utils/errors.ts to hang the constraint-name switch off.

How it shipped. Reviewing the first attempt turned up three more leaks, one worse than this finding. The fall-through returned err.message, which Drizzle builds from the failed query and every bound parameter — so a dropped connection mid-save returned the whole submitted row, and on POST /admin/users the new password hash. asPostgresError also inspected only err.cause, so the mapping was dead for every db.query.* read, and the HTTPException branch still handed err.cause to the client. All four are covered by tests verified to fail when the leak is put back.
